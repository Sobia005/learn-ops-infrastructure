## 3. What is the Pipfile?

The `Pipfile` is the dependency manifest for **Pipenv**. It does three things:

1. **Declares dependencies** — splits them into `[packages]` (production) and `[dev-packages]` (local-only tools like linters and test runners), so dev tools never end up in production.

2. **Pins the Python version** — `[requires]` locks the project to Python 3.11.11, ensuring every developer and CI environment uses the same interpreter.

3. **Defines command shortcuts** — `[scripts]` lets you run `pipenv run migrate` instead of typing `python3 manage.py migrate` in full.

The companion file `Pipfile.lock` is auto-generated and records the exact resolved version of every package (including transitive dependencies), making installs fully reproducible across machines

## 5. What does `decorators.py` do?
A decorator is a function that **wraps another function** to add behavior before or after it runs — without modifying the original function's code. In Python, you apply one with the `@` syntax:

```python
@is_instructor()
def my_view(request):
    ...
```

That is exactly equivalent to:

```python
def my_view(request):
    ...
my_view = is_instructor()(my_view)
```

The decorator intercepts the call, does something (a check, logging, timing, etc.), and then decides whether to call the original function or not.

### What does `decorators.py` do?

It defines two **role-based access control guards** for API views:

- `@is_instructor()` — checks whether the logged-in user belongs to the `Instructors` group in Django's auth system.
- `@is_staff()` — checks whether the logged-in user belongs to the `Staff` group.

If the check passes, the original view function runs normally. If it fails, the request is immediately rejected with a `401 Unauthorized` response and a plain-English message, and the view never executes.

### How the decorator pattern works in this file

Both decorators use the same three-layer nesting pattern:

```
is_instructor()        ← outer function (called at decoration time)
  └── decorator(func)  ← receives the view function being wrapped
        └── __wrapper(request, *args, **kwargs)  ← runs on every actual HTTP request
```

The outer function exists so you can call it with `@is_instructor()` (with parentheses), leaving room to pass arguments to the decorator in the future if needed. `__wrapper` is what actually runs on each request — it performs the group check and either delegates to `func` (the real view) or returns the 401 early.

A view using this would look like:

```python
@is_instructor()
def delete_student(request, pk):
    # only reaches here if the user is in the Instructors group
    ...
```

## 6. What is a serializer, and how does it fit the request/response cycle?
### Client sends data → Database

```
Client
  │  sends POST /students/ with JSON body: {"name": "Jane", "cohort": 3}
  ▼
Request
  │  arrives at the Django server
  ▼
View
  │  receives the request, passes the JSON body to the serializer
  ▼
Serializer
  │  checks: are all required fields present? are the types correct?
  │  if invalid → stops here, returns 400 Bad Request to client
  │  if valid   → converts JSON into a Python object
  ▼
Model / Database
     creates a new row in the students table, saves it
```

### Database → Client gets data back

```
Database / Model
  │  Django ORM fetches the student object (a Python object)
  ▼
Serializer
  │  reads the model's fields and converts them into a Python dict
  ▼
JSON
  │  DRF turns that dict into a JSON string: {"id": 1, "name": "Jane", "cohort": 3}
  ▼
Response
  │  wrapped in an HTTP 200 response with Content-Type: application/json
  ▼
Client
     receives the JSON and can display or use it
```

### The key insight

The **View** is the traffic controller — it receives the request and sends the response. But it delegates all the hard work:

- It asks the **Serializer** to validate and translate data.
- It asks the **Model** to read or write the database.

The view itself stays thin. The serializer is the only layer that knows about both the shape of the JSON *and* the shape of the model.

## 8. Views vs. viewsets

| Type | Example class | When to use it |
|------|--------------|----------------|
| **View** (`APIView`) | Not used in this project | Use when you need full manual control over a single endpoint. You write separate methods for `get()`, `post()`, `delete()` yourself. Best for one-off or unusual endpoints that don't follow standard CRUD. |
| **ViewSet** | `BookViewSet`, `CohortViewSet`, `ProjectViewSet` | Use when one resource needs the full set of actions — `list`, `retrieve`, `create`, `update`, `destroy` — grouped in one class. DRF automatically wires up the right action based on the HTTP method and URL. |

This project also uses **`ModelViewSet`** (e.g. `StudentViewSet`), which is a ViewSet that goes one step further — it auto-generates the standard CRUD logic from the model so you only need to write the parts you want to customize.

**Simple way to think about it:**

- `APIView` — you build everything yourself, one method at a time.
- `ViewSet` — you get the structure, you write the logic.
- `ModelViewSet` — you get the structure *and* the logic; just override what's different.
